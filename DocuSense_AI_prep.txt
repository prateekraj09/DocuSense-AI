1. PROJECT ELEVATOR PITCH (HOW TO INTRODUCE THIS PROJECT IN AN INTERVIEW)
--------------------------------------------------------------------------------
"DocuSense AI is a production-grade, multi-tenant SaaS backend for Document and
Code Intelligence built with FastAPI, PostgreSQL 16 (pgvector), and Google Gemini.
Unlike tutorial RAG scripts that process documents synchronously in memory and 
leak data between users, DocuSense AI implements enterprise-grade multi-tenant 
data isolation via JWT authentication, offloads parsing and embedding generation 
to asynchronous Celery/Redis background workers, and executes single-store hybrid 
retrieval combining pgvector cosine distance and PostgreSQL tsvector full-text 
search via Reciprocal Rank Fusion (RRF). It also incorporates Redis semantic/exact 
caching and token usage tracking to minimize LLM latency and API costs."

2. ARCHITECTURAL DESIGN TRADE-OFFS (THE "WHY" BEHIND EVERY DECISION)
--------------------------------------------------------------------------------

[Trade-off 1]: Why PostgreSQL + pgvector instead of a dedicated Vector DB (Chroma, Pinecone, Weaviate)?
- Answer:
  1. ACID Transactions & Consistency: In a multi-tenant SaaS application, documents,
     users, subscriptions, metadata, and embeddings must remain strictly synchronized.
     If a user deletes a document, a single CASCADE DELETE in PostgreSQL atomically
     removes the document, its chunks, and all its vector embeddings. With separate
     vector stores (e.g., Pinecone + Postgres), you suffer from dual-write consistency
     problems, orphan embeddings, and eventual consistency lag.
  2. Single Network Hop & Hybrid Search: By keeping vectors inside PostgreSQL, we can
     execute vector similarity search (pgvector) AND BM25-style keyword search (tsvector)
     in a single database query, filtered directly by tenant (`user_id = :current_user_id`).
  3. Operational Overhead & Cost: Operating, backing up, and monitoring one PostgreSQL
     cluster is significantly cheaper and more reliable than paying for and managing
     two disparate database clusters.
  4. Maturity: PostgreSQL has 30+ years of battle-tested enterprise tooling, replication,
     point-in-time recovery, and security.

[Trade-off 2]: Why Celery + Redis instead of synchronous HTTP processing or FastAPI BackgroundTasks?
- Answer:
  1. Heavy CPU & Network Blocking: Extracting text from a 100-page PDF, chunking it,
     and calling embedding APIs for hundreds of chunks can take anywhere from 10 to 60+ seconds.
     Doing this inside the HTTP request would block web server worker threads, exhaust
     connection pools, cause client HTTP timeouts (504 Gateway Timeout), and kill API throughput.
  2. FastAPI BackgroundTasks runs within the same process/memory space as the web server.
     If the API server restarts, scales down, or crashes due to memory pressure, in-flight
     jobs are permanently lost.
  3. Celery + Redis provides a distributed, durable task queue with retries, exponential
     backoff, worker concurrency management, rate limiting, and failure logging.

[Trade-off 3]: Why direct SDK (Google Gemini `google-genai`) instead of LangChain or LlamaIndex?
- Answer:
  1. Production Transparency: LangChain abstracts SQL queries, prompt templates, and
     vector calculations behind high-level chains. When latency spikes or queries return
     hallucinations in production, debugging through 15 layers of nested abstraction is painful.
  2. Performance & Dependency Bloat: Heavy wrapper frameworks add hundreds of transitive
     dependencies, breaking changes across minor versions, and unexpected latency overhead.
  3. Writing native SQL expressions and direct SDK calls demonstrates deep understanding of
     underlying vectors, distance metrics (Cosine Distance `<=>`), and LLM context windows.

[Trade-off 4]: Why UUIDs instead of auto-incrementing integer IDs?
- Answer:
  Auto-incrementing integers (1, 2, 3...) leak business metrics (competitors can gauge how
  many users or documents you have) and are susceptible to Insecure Direct Object Reference
  (IDOR) attacks if an authorization check fails. UUIDv4 provides cryptographically secure,
  globally unique identifiers across distributed databases.

[Trade-off 5]: Why 768 dimensions for pgvector?
- Answer:
  Google Gemini's modern embedding models (`models/gemini-embedding-001`) utilize Matryoshka
  Representation Learning (MRL), allowing output dimensionality configuration. We set it to
  768 dimensions, which perfectly matches PostgreSQL's `VECTOR(768)`. 768 dimensions provides
  an ideal sweet spot: cutting memory and storage requirements by 75% compared to 3072 dimensions,
  while retaining 99%+ of the semantic retrieval quality and dramatically speeding up index lookups.

[Trade-off 6]: Why sliding window chunking with overlap instead of naive fixed-size cuts?
- Answer:
  Naive splitting by character count (e.g. cutting every 500 characters) cuts words, code tokens,
  and sentences in half (e.g., "funct" on chunk 1 and "ion" on chunk 2). A boundary-aware sliding
  window searches for natural sentence/paragraph delimiters (`\n\n`, `. `, `? `). Overlap ensures
  that any fact spanning the boundary between two chunks is present in both chunks, preventing
  retrieval failure.

[Trade-off 7]: Why PyMuPDF (`fitz`) over pypdf or pdfplumber?
- Answer:
  PyMuPDF is built on the high-performance C++ MuPDF engine. In production benchmarks, it is
  5x to 10x faster than pure-Python libraries like pypdf, handles complex multi-column layouts,
  and reliably extracts page numbers essential for RAG source citations.

3. MILESTONE 1 QUIZ - EASY TO UNDERSTAND MODEL ANSWERS
--------------------------------------------------------------------------------
Q1: Why PostgreSQL 16 + pgvector instead of a separate vector DB like Chroma/Pinecone?
A1: (1) Data Consistency (No Dual-Write Bug): When a user deletes a document in PostgreSQL,
    CASCADE DELETE automatically deletes its chunks and embeddings in one transaction. With
    external vector DBs, you have two databases that can easily get out of sync.
    (2) Simpler Infrastructure & Lower Cost: Instead of paying for, monitoring, and maintaining
    two separate databases, everything (relational user accounts, documents, full-text search,
    and vector embeddings) lives inside one reliable database.

Q2: What does the JWT payload claim `sub` contain, and how is it used for multi-tenancy?
A2: `sub` stands for "Subject" and contains the user's UUID (e.g. "a3b1...").
    When a request comes in, our dependency `get_current_user` extracts this UUID from the token.
    Then, every database query (e.g., `SELECT * FROM documents WHERE user_id = :user_id`)
    filters strictly by this UUID. Because User A's token contains User A's UUID, User A can
    never view or search User B's documents.

Q3: Why dimension 768, and what happens if a 1536-dim vector is inserted?
A3: The dimension of the vector in PostgreSQL must match the embedding model exactly. We
    configured Gemini embeddings with `output_dimensionality=768`, so the column is `VECTOR(768)`.
    If you attempt to insert a 1536-dimensional vector into a `VECTOR(768)` column, PostgreSQL
    will immediately reject the query with an error (`ERROR: different vector dimensions 768 and 1536`),
    preventing corrupted or un-indexable vector data.

4. MILESTONE 2 SUMMARY & KEY COMPONENTS BUILT
--------------------------------------------------------------------------------
1. Document Parsers (`services/parsers/`):
   - `PDFParser`: Page-by-page text extraction with PyMuPDF, tracking page numbers for citations.
   - `CodeAndTextParser`: Line-number aware parser for code (.py, .ts, .js) and markdown (.md).
   - `parse_document`: Universal dispatcher validating against allowed file extensions.
2. Chunking Engine (`services/chunker.py`):
   - Sentence/paragraph-aware sliding window with configurable `chunk_size` and `chunk_overlap`.
   - Attaches metadata (filename, page_number, start_line, end_line) to every chunk.
3. Google Gemini Embedding Service (`services/embedding.py`):
   - Direct integration with `google-genai` SDK using `models/gemini-embedding-001`.
   - Configures `output_dimensionality=768` for optimal storage & speed.
   - Batch embedding support (`generate_embeddings_batch`) for high ingestion throughput.
4. Document Ingestion Service (`services/ingestion.py`):
   - Synchronous processing pipeline: validates file size -> creates Document in PROCESSING state
     -> extracts blocks -> chunks -> generates embeddings -> saves DocumentChunks -> marks COMPLETED.
   - Full rollback and FAILED state update on error.
5. Multi-Tenant Similarity Search (`services/retrieval.py`):
   - Computes query vector using Gemini embedding service.
   - Executes cosine distance search (`DocumentChunk.embedding.cosine_distance(query_embedding)`),
     strictly scoped to `user_id == current_user.id`.
   - Generates normalized similarity scores (`1.0 - cosine_distance`).
6. Document REST Endpoints (`api/v1/endpoints/documents.py`):
   - `POST /api/v1/documents/upload`: Multipart file upload, processing, returns chunk count.
   - `GET /api/v1/documents`: Lists authenticated user's documents.
   - `GET /api/v1/documents/{document_id}`: Owner-verified document detail lookup.
   - `DELETE /api/v1/documents/{document_id}`: Cascade deletes document and chunks.
   - `POST /api/v1/documents/search`: Vector search endpoint returning top relevant chunks.

5. COMMON INTERVIEW QUESTIONS FOR MILESTONE 2
--------------------------------------------------------------------------------
Q1: "How do you choose between Cosine Distance, Euclidean Distance, and Inner Product for vectors?"
A1: "Cosine Distance (`<=>` in pgvector) measures the angular difference between vectors,
     making it invariant to vector magnitude (document length). It is ideal for text embeddings.
     Euclidean Distance (`<->`) measures straight-line physical distance and is sensitive to length.
     Inner/Dot Product (`<#>`) is fastest but only equivalent to cosine distance if all vectors
     are pre-normalized to unit length (L2 norm = 1)."

Q2: "What is chunk overlap, and why is it essential in RAG?"
A2: "Chunk overlap means sharing a small window of text (e.g. 100-150 characters) between
     adjacent chunks. Without overlap, critical semantic relationships that happen to cross
     the boundary between chunk N and chunk N+1 get severed, leading to retrieval failures
     when the user's question depends on information spanning both chunks."

Q3: "Why did you implement batch embedding instead of generating embeddings chunk by chunk?"
A3: "Generating embeddings chunk-by-chunk introduces substantial network latency: 100 chunks
     at 200ms per HTTP request would take 20 seconds of sequential round-trips, plus it quickly
     hits API rate limits (RPM - Requests Per Minute). Batching sends up to 30-50 chunks in a
     single HTTP request, reducing network roundtrips from 100 down to 2 or 3 and slashing ingestion time."
