1. EXECUTIVE SUMMARY: WHAT PROBLEM ARE WE SOLVING & HOW?
================================================================================

[The Real-World Problem]:
Large Language Models (like GPT-4 or Gemini) have two fundamental limitations:
1. Knowledge Cutoff & Hallucination: They do not know about private enterprise
   documents, company source code, or internal confidential PDFs. When asked about
   unfamiliar subjects, they frequently "hallucinate" confident-sounding falsehoods.
2. Context Window & Cost Limitations: You cannot send a 500-page financial report
   or a 50,000-line code repository in every single prompt. It is too expensive,
   exceeds context limits, and takes 20+ seconds to process.

[The Flaw in Tutorial RAG Projects]:
90% of beginners build RAG as a 50-line Python script using LangChain, Streamlit,
and an in-memory database (FAISS/Chroma). This fails in the real world:
- It processes files synchronously inside the HTTP web request, crashing the server.
- It has NO authentication: User A can see and search User B's proprietary files.
- It uses naive keyword-only or vector-only search, missing exact function names or error codes.
- It has no audit logging, no cost tracking, no response caching, and no rate limiting.

[How DocuSense AI Solves This (The Solution We Built)]:
DocuSense AI is a production-grade, multi-tenant SaaS backend API designed for
verifiable document and code intelligence:
1. Multi-Tenant Isolation: Every user is authenticated via stateless JWT tokens.
   All database tables and similarity searches enforce strict tenant scoping
   (`WHERE user_id = :current_user_id`).
2. Asynchronous Ingestion Engine: When a user uploads a 50MB PDF or code file, the
   FastAPI web server validates it, creates a PENDING database record, pushes the
   processing job to a Redis queue, and immediately returns HTTP 202 Accepted.
   A distributed Celery worker pool parses, chunks, and embeds the file in the background.
3. Single-Store Hybrid Search (RRF): Instead of maintaining two separate databases,
   we use PostgreSQL 16 with `pgvector`. We execute semantic vector search (cosine distance)
   AND exact full-text keyword search (`tsvector`), merging them using Reciprocal Rank Fusion (RRF).
4. Guarded Generation & Citations: Gemini generates answers strictly using the top
   retrieved chunks. If information is missing, it explicitly replies "Insufficient information...".
   Every fact is tagged with an exact citation (e.g. `[architecture.pdf, Page 2]`).
5. Cost & Latency Optimization:
   - Redis Query Caching: Returns cached answers in < 1ms for repetitive queries (0 token cost).
   - SlowAPI Rate Limiting: Protects LLM billing and limits abuse.
   - Server-Sent Events (SSE): Streams generated answer tokens in real-time.
   - Evaluation Script: Benchmarks Recall@K and latency metrics.

2. FIRST-PRINCIPLES CONCEPT DICTIONARY (THEORY, DEFINITIONS & REALITY)
================================================================================

1. RETRIEVAL-AUGMENTED GENERATION (RAG):
   - Definition: An AI architecture that combines an information retrieval system
     (a search engine over your private data) with a generative LLM.
   - How it works: Instead of asking the LLM to answer from memory, we first search
     our database for the top 5 most relevant paragraphs, paste them into the LLM prompt
     as "Context", and instruct the LLM: "Answer the user question using ONLY this context."

2. VECTOR EMBEDDING (DENSE VECTOR):
   - Definition: An embedding is a translation of human text into an array of floating-point
     numbers (coordinates) where semantic meaning is converted into geometry.
   - How it works: Texts with similar conceptual meanings end up close together in space.
     For example, "how to authenticate a user" is geometrically very close to
     "JWT login verification", even though they share zero identical words.
   - What we use: Google Gemini `models/gemini-embedding-001` configured to 768 dimensions.

3. VECTOR DIMENSIONALITY (Why 768?):
   - Definition: The count of floating-point numbers in the vector array.
   - Concept: Higher dimensions (e.g. 3072) capture subtle nuances but require 4x more
     RAM, disk space, and computational power to compare. Modern models use Matryoshka
     Representation Learning (MRL), which trains embeddings so that the first 768 dimensions
     retain 99%+ of semantic search accuracy while cutting index memory by 75%.

4. VECTOR DISTANCE METRICS:
   - Cosine Distance (`<=>` in pgvector):
     Measures the angle between two vectors. It ranges from 0 (identical direction) to 2
     (opposite direction). It ignores document length and focuses purely on semantic direction.
     Standard for text RAG.
   - Euclidean Distance (`<->` in pgvector):
     Measures straight-line physical distance. Sensitive to document length/magnitude.
   - Dot / Inner Product (`<#>` in pgvector):
     Fastest mathematically, but only valid if all vectors are pre-normalized to unit length 1.

5. TOKENIZATION & SLIDING WINDOW CHUNKING WITH OVERLAP:
   - What is Chunking? LLMs cannot read infinite text. We must divide long documents
     into manageable pieces (e.g. 800 characters each).
   - Why Sliding Window with Overlap? Naive splitting cuts words and sentences in half.
     Our chunker searches backwards for natural punctuation (`\n\n`, `. `, `! `, `? `).
     A 150-character overlap between chunk N and chunk N+1 ensures that any sentence
     spanning the seam between two chunks is preserved intact in both.

6. MULTI-TENANCY & ROW-LEVEL DATA ISOLATION:
   - Definition: Multiple independent customers share the same database infrastructure,
     but their data is strictly isolated.
   - Implementation: Every table (`documents`, `document_chunks`, `query_logs`) has a foreign
     key `user_id`. Every SQL query executes with `WHERE user_id = :authenticated_user_id`.

7. JSON WEB TOKEN (JWT) & CRYPTOGRAPHIC SIGNATURE:
   - Anatomy: Header.Payload.Signature
     1. Header: Algorithm used (HMAC-SHA256).
     2. Payload: User UUID (`sub`), issue time (`iat`), expiration time (`exp`).
     3. Signature: `HMACSHA256(base64(Header) + "." + base64(Payload), SECRET_KEY)`.
   - Why it matters: Stateless verification. The server verifies validity mathematically
     in microseconds without hitting the database.

8. SALTED BCRYPT PASSWORD HASHING:
   - Why not SHA-256? SHA-256 is designed to be fast; GPUs can compute billions of SHA-256
     hashes per second. Bcrypt is intentionally slow and memory-hard with an adaptive cost
     factor and per-user random salts.

9. ASYNCHRONOUS TASK QUEUE (CELERY) & MESSAGE BROKER (REDIS):
   - What is Redis? A high-speed in-memory store used as a task queue broker.
   - What is Celery? A distributed background worker system that pulls jobs off Redis
     and executes heavy parsing, embedding, and database writes without blocking HTTP threads.

10. FULL-TEXT SEARCH (`tsvector` & `tsquery` in PostgreSQL):
    - Concept: An inverted index that reduces words to linguistic stems (e.g., "running",
      "ran" -> "run") and strips common stop words.
    - Why combine with vectors? Vector search understands concepts; full-text search
      guarantees exact matches on function names, error codes, and technical jargon.

11. RECIPROCAL RANK FUSION (RRF):
    - Formula: RRF_Score(doc) = SUM_{engine in {vector, keyword}} [ 1 / (60 + rank_{engine}(doc)) ]
    - Why it works: Aggregates results by rank order rather than calibrating dissimilar
      score distributions. Documents that satisfy both semantic intent and exact keywords rise to the top.

12. REDIS RESPONSE CACHING & DETERMINISTIC CACHE KEYS:
    - Concept: If 10 users in an organization ask "What is our company holiday policy?",
      calling Gemini 10 times wastes money and takes 10x more time.
    - Implementation: We compute a SHA-256 hash of `user_id` + normalized `query` + `document_ids`.
      On cache hit, the response returns in < 1ms with 0 LLM API tokens used.

13. RATE LIMITING & SLOWAPI:
    - Concept: Protecting API endpoints against denial-of-service (DoS) attacks and
      preventing runaway cloud LLM billing.
    - Implementation: Redis-backed token-bucket / fixed-window rate limiter enforcing limits
      (e.g., 30 queries/minute per user/IP), returning HTTP 429 Too Many Requests.

14. SERVER-SENT EVENTS (SSE) STREAMING:
    - Concept: A unidirectional, persistent HTTP connection where the server pushes tokens
      to the browser in real-time as they are generated by Gemini.
    - SSE vs. WebSockets: WebSockets is bidirectional (chat rooms, gaming) and requires a
      custom protocol. SSE uses standard HTTP, handles automatic reconnection, and is lighter
      for LLM text completion streams.

15. RETRIEVAL EVALUATION METRIC (RECALL@K):
    - Formula: Recall@K = (Queries where ground-truth chunk appears in Top K) / (Total Queries)
    - Measures how accurately your hybrid retrieval engine surfaces the true answer chunk.

3. SYSTEM ARCHITECTURE & END-TO-END DATA LIFECYCLE
================================================================================

[Step 1: Auth & User Onboarding]:
- User registers (`POST /api/v1/auth/register`) -> password hashed with bcrypt -> saved in DB.
- User logs in (`POST /api/v1/auth/login`) -> receives signed JWT with user UUID in `sub`.

[Step 2: Non-Blocking Async Ingestion]:
- User uploads file (`POST /api/v1/documents/upload`).
- FastAPI saves `Document` record in `PENDING` state.
- Celery task `ingest_document_task.delay(...)` pushed to Redis queue.
- API returns `HTTP 202 Accepted` with `document_id` in < 50ms.
- Celery worker pulls job:
  * Extracts text with PyMuPDF (tracking page numbers) or CodeParser (tracking line numbers).
  * Chunks text with sliding window (800 characters, 150 overlap).
  * Batches chunks (30/batch) and calls Gemini `models/gemini-embedding-001` (768 dims).
  * Stores chunks + embeddings + tsvector in PostgreSQL `document_chunks`.
  * Marks `Document` status as `COMPLETED`.

[Step 3: Cached Hybrid Query & Streaming]:
- User sends query to `/api/v1/chat/query` or `/api/v1/chat/stream`.
- Checks Redis cache: if hit, returns in < 1ms with `cache_hit=True`.
- If cache miss:
  * Generates query embedding via Gemini.
  * Runs pgvector Cosine Search (`<=>`) and PostgreSQL Full-Text Search (`tsvector`).
  * Merges candidate ranks using Reciprocal Rank Fusion (RRF constant k=60).
  * Formats Top 5 chunks into strict prompt with anti-hallucination instruction.
  * Calls Gemini `models/gemini-3.5-flash-lite` at zero temperature.
  * Streams tokens or returns answer with verifiable citations (`[filename, Page X]`).
  * Logs tokens and latency to `query_logs` table.
  * Writes response to Redis cache with 1-hour TTL.

4. ARCHITECTURAL DESIGN TRADE-OFFS ("WHY THIS OVER THAT?")
================================================================================

[Trade-off 1]: PostgreSQL + pgvector vs. Standalone Vector DBs (Chroma, Pinecone, Milvus):
- Atomicity: Eliminates the dual-write bug. `CASCADE DELETE` removes documents, chunks,
  and embeddings in a single ACID transaction.
- Cost: Single managed database instance instead of two disparate cloud clusters.
- Unified Hybrid Query: Combines user relational filters, keyword search, and vector search in 1 hop.

[Trade-off 2]: Celery + Redis vs. Synchronous HTTP or FastAPI BackgroundTasks:
- Non-blocking: Keeps HTTP response times sub-50ms regardless of document size.
- Durability: Redis persists queue jobs; Celery handles worker crashes and exponential retries.
  FastAPI BackgroundTasks dies if the container restarts.

[Trade-off 3]: Direct SDK (Google GenAI) vs. LangChain:
- Complete transparency: No hidden prompt injections, no nested wrapper chains. Clean,
  maintainable, and easily debugged in production.

[Trade-off 4]: Server-Sent Events (SSE) vs. WebSockets:
- SSE operates over standard HTTP/HTTPS with automatic reconnection. WebSockets is heavier
  and overkill for unidirectional LLM text streaming.

[Trade-off 5]: Redis Caching vs. Querying LLM Every Time:
- Repeated queries (e.g. team members querying the same company handbook) return in < 1ms
  instead of 2000ms, and cost $0 in LLM API tokens.

[Production Engineering Hard Lessons]:
- PostgreSQL Null Byte (0x00) Sanitization: Mathematical and scientific PDFs frequently extract
  with raw null characters (`\x00`). PostgreSQL `VARCHAR` and `TEXT` are null-terminated C strings
  and strictly reject null bytes (`invalid byte sequence for encoding UTF8: 0x00`). We sanitize
  all text via `.replace('\x00', '')` across all parser and chunker layers.
- ORM Custom Extension Operators: Mapping `pgvector` requires native `Vector(768)` mapped columns
  so SQLAlchemy exposes `.cosine_distance()` and `<=>` operators. Generic column variants strip
  specialized operators.
- Distributed Redis JSON Serialization: Pydantic v2 `model_dump()` preserves native UUID objects.
  Redis caching requires `model_dump(mode='json')` or `json.dumps(..., default=str)` to prevent
  `TypeError: Object of type UUID is not JSON serializable`.

5. MASTER INTERVIEW QUIZ REVISION (MODEL ANSWERS FOR ALL MILESTONES)
================================================================================

--- MILESTONE 1 QUIZ REVISION ---
Q1: Why PostgreSQL 16 + pgvector instead of a separate vector DB like Chroma/Pinecone?
A1: "(1) Transactional Integrity: Deleting a document atomically cascades to its chunks
     and vectors, eliminating orphan embeddings. (2) Operational Simplicity: A single database
     handles users, metadata, full-text search, and high-dimensional vectors."

Q2: What does the JWT claim `sub` contain, and how is it used for multi-tenancy?
A2: "`sub` stores the user's UUID. Every authenticated request extracts this UUID and
     applies `WHERE user_id = :user_id` to all database queries, making cross-tenant data leaks impossible."

Q3: Why dimension 768, and what happens if a 1536-dim vector is inserted?
A3: "Vector dimensions in PostgreSQL must match the embedding model output. Google Gemini
     generates 768-dimensional embeddings. Inserting a 1536-dim vector causes PostgreSQL
     to throw an immediate error and reject the transaction to protect index integrity."

--- MILESTONE 2 QUIZ REVISION ---
Q1: What is the difference between Cosine Distance (`<=>`) and Euclidean Distance (`<->`)?
A1: "Cosine Distance measures the angle between vectors, ignoring document length/magnitude.
     Euclidean Distance measures straight-line physical distance and is distorted by text length.
     Cosine distance is the standard metric for text embeddings."

Q2: What is chunk overlap, and what failure mode does it prevent?
A2: "Chunk overlap shares a 150-character window between adjacent chunks, preventing retrieval
     failure when a key concept crosses the cut boundary between two chunks."

Q3: Why implement batch embedding instead of one API call per chunk?
A3: "Batching 30 chunks per request reduces network round-trips from 100 down to 3 or 4,
     slashing ingestion time by 85% and preventing API rate limit errors."

--- MILESTONE 3 QUIZ REVISION ---
Q1: Why is Hybrid Search (Vector + Keyword via RRF) superior to pure vector search?
A1: "Pure vector search excels at conceptual matching but struggles with exact identifiers,
     function names (e.g. `process_webhook`), and specific error codes (`ERR_403`). Full-text
     search (tsvector) guarantees exact token matches. Reciprocal Rank Fusion merges both
     rankings to elevate documents that satisfy both semantic meaning and exact keywords."

Q2: What happens between HTTP 202 Accepted and COMPLETED in async upload?
A2: "FastAPI creates a PENDING document row and pushes a job to Redis. The client receives 202.
     A Celery worker pulls the task, parses the file, chunks the text, calls Gemini's batch
     embedding API, writes chunks + vectors + tsvectors into PostgreSQL, and updates document
     status to COMPLETED."

Q3: How do we prevent LLM hallucinations and enforce verifiable citations?
A3: "We enforce zero temperature and a strict system prompt instructing the model to answer
     ONLY from retrieved chunks or reply 'Insufficient information...'. We mandate citations
     in the format [filename, Page X], which our backend parses and validates against chunk metadata."

--- MILESTONE 4 QUIZ REVISION ---
Q1: How does Redis response caching work in DocuSense AI, and how do we handle cache invalidation?
A1: "We compute a SHA-256 hash key of (user_id + normalized_query + document_ids). On cache hit,
     we return the stored JSON in sub-1ms with 0 token cost. When a user uploads or deletes a
     document, we invalidate all cached query keys belonging to that user to prevent stale answers."

Q2: Why use Server-Sent Events (SSE) instead of WebSockets for LLM response streaming?
A2: "SSE is designed specifically for unidirectional server-to-client streaming over standard HTTP.
     It supports built-in reconnection, works through corporate proxies and firewalls without
     special configuration, and has significantly less overhead than a full-duplex WebSocket connection."

Q3: What is Recall@K, and why is it the primary metric for evaluating a RAG retrieval pipeline?
A3: "Recall@K measures the proportion of test queries where the ground-truth relevant chunk is
     successfully retrieved within the top K results. In RAG, if the correct chunk is not in
     the top K, the LLM has zero chance of answering accurately, making Recall@K the most
     critical determinant of downstream RAG accuracy."

7. CONTAINERIZATION, CLOUD DEPLOYMENT & PRODUCTION RESUME LINK GUIDE
================================================================================

[Core Concept: Localhost vs. Cloud Deployment vs. Containerization]:
1. What is `localhost` (127.0.0.1)?:
   `localhost` is a loopback network address that points strictly to your own physical machine.
   If you put `http://localhost:8000/ui` on a resume or portfolio, an external recruiter or
   interviewer clicking the link will see "This site can't be reached", because their browser
   will try to query port 8000 on THEIR laptop, where DocuSense AI is not running!
2. Why don't visitors run your code on their machines?:
   Hiring managers and interviewers review 50+ resumes daily and spend 30-60 seconds per resume.
   They will NEVER clone a GitHub repo, install Python, set up virtual environments, download
   Docker, compile pgvector C extensions, configure Redis, and set up API keys. They demand
   a 1-click clickable web link (`https://...`) that opens instantly on desktop or mobile.
3. What is Containerization (Docker)?:
   Containerization packages the application code, runtime (Python 3.12), system C-libraries
   (`libpq-dev`, `build-essential`), third-party services (PostgreSQL 16 + pgvector, Redis 7),
   and configuration into an immutable, standalone Linux container.
   It completely solves the "It works on my machine!" problem: if the container runs in local
   Docker, it is mathematically guaranteed to run identically in AWS, GCP, or Render without
   dependency version mismatch.
4. What is Cloud Deployment?:
   Cloud deployment is running the containerized application on managed 24/7 internet-facing
   servers equipped with public IP addresses, automatic SSL/TLS encryption (`https://`),
   managed databases, and DNS routing.

[Docker Compose Multi-Container Orchestration Architecture]:
In `docker-compose.yml`, DocuSense AI coordinates four isolated services over an internal bridge network:
1. `postgres` (Container: `docusense_postgres`):
   - Image: `pgvector/pgvector:pg16`
   - Volume: `postgres_data` (persists relational data and vector indexes across restarts).
   - Healthcheck: `pg_isready` verifies the database is accepting queries before starting dependencies.
2. `redis` (Container: `docusense_redis`):
   - Image: `redis:7-alpine`
   - Volume: `redis_data` (persists cache state and in-flight Celery task queues).
   - Healthcheck: `redis-cli ping` ensures memory broker readiness.
3. `api` (Container: `docusense_api`):
   - Multi-stage Dockerfile based on `python:3.12-slim`.
   - Runs FastAPI with Uvicorn on port 8000.
   - Depends on `postgres` and `redis` being healthy.
4. `worker` (Container: `docusense_worker`):
   - Runs Celery worker process (`celery -A workers.celery_app.celery_app worker`).
   - Consumes ingestion jobs from Redis and writes chunks directly to PostgreSQL.

8. THE DEFINITIVE INTERVIEW PITCH & ARCHITECTURAL DEFENSE
================================================================================

[The #1 Interview Question: "Why did you build this? When ChatGPT or Gemini can upload files for free, why build DocuSense AI?"]

MODEL ANSWER TO BLOW THE INTERVIEWER AWAY:
"That's a very common question, but it confuses a consumer chat application with an
enterprise software infrastructure system. You cannot run a business on the ChatGPT web UI
for five fundamental reasons:

1. Data Sovereignty, Privacy & Compliance (GDPR, HIPAA, SOC 2):
   Enterprises, healthcare systems, and fintech companies have strict legal mandates prohibiting
   proprietary IP, customer data, and internal source code from being sent to consumer AI portals
   where models might be trained on it. DocuSense AI provides private, self-hosted, tenant-isolated
   storage inside PostgreSQL where embeddings and documents remain under company control.

2. Cost at Scale (Context Window Economics):
   Consumer models like Gemini 1.5 Pro boast 2-million-token context windows. But 'context stuffing'
   10,000 corporate documents into every single API call costs $5.00 to $10.00 PER QUERY. If a company
   runs 50,000 queries a day, that's $250,000 every single day!
   DocuSense AI uses single-store hybrid search to retrieve ONLY the top 8 relevant chunks, costing
   less than $0.0001 per query. Furthermore, with our Redis query-hash caching layer, repeat queries
   cost literally $0.00 and execute in 0.8 milliseconds.

3. Multi-Tenancy & Role-Based Access Control (RBAC):
   ChatGPT has no concept of database-level row multi-tenancy. In an enterprise with 1,000 employees,
   an intern querying internal documentation must never see executive payroll or board memos.
   DocuSense AI enforces stateless JWT tokens where every single database query and vector distance
   calculation strictly filters by `WHERE user_id = :authenticated_user_id`.

4. Programmatic API Integration (Building Software vs. Chatting in a Box):
   ChatGPT is a human chat interface. You cannot integrate ChatGPT's UI into a banking mobile app,
   an internal Jira workflow, or a customer service portal. DocuSense AI is a headless REST API with
   asynchronous background workers (Celery + Redis), rate limiting, Server-Sent Events (SSE) token
   streaming, and OpenAPI schemas built for programmatic consumption.

5. Verifiable Audit Trails & Anti-Hallucination Guardrails:
   In legal, medical, or engineering audits, an AI response without traceable lineage is useless.
   DocuSense AI logs every query, latency, token count, and exact retrieved chunk ID into `query_logs`.
   Our LLM generation forces strict inline citations `[filename, Page X]` verified against chunk metadata,
   and will strictly admit 'Insufficient information' rather than hallucinate."
